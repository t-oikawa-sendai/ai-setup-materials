# Chat Handoff Template（チャット引き継ぎテンプレート）

> **読む順：** [AI運用全体のCase Study](PERSONA_OPERATION_CASE_STUDY.md) → [Prompt Template](PERSONA_PROMPT_TEMPLATE.md) → **本Handoff Template**
>
> AIへ通常の依頼を出すだけであれば、先に [`PERSONA_PROMPT_TEMPLATE.md`](PERSONA_PROMPT_TEMPLATE.md) を使用します。本テンプレートは、チャットやAIを切り替えて継続作業するときに使用します。

## 1. 目的と適用範囲

本テンプレートは、作業を新しいチャットへ移す際に、次のAIが正本を確認して作業を再開するための現在地点を渡す。基本は同じAI間の移行とし、異なるAI間にも適用できる。

引き継ぎ文は会話履歴の複製でも正本の代替でもない。確定した仕様・判断・作業状態は、その案件で定めた保存先に保持する。

## 2. 保存方式

移行前に、次のうち該当する方式を一つ確認する。

- **GitHub管理中**：GitHub上の文書と指定commitを基準とする。
- **ローカルGitのみ**：ローカルRepositoryの文書と指定commitを基準とする。受け取る側がそのcommitへアクセスできる方法も確認する。
- **Gitなし**：保存済みの対象ファイル一式を基準とする。ファイルの所在、一覧、受け渡し方法を確認する。

GitやRepositoryが存在しない案件に、branch、commit SHA、pushを要求しない。該当しない項目は`N/A`、必要だが確認できない項目は`UNVERIFIED`とする。

## 3. 送る側の確定手順

1. 保存方式、対象作業、適用される既存規則、正本を確認する。
2. 会話内だけに残っている確定事項・判断・現在地点があれば、案件の規則に従い正本へ記録する。既存の判断履歴は改変しない。
3. **GitHub管理中**で保存すべき変更がある場合、Userにcommitとpushを案内する。テンプレート作成の指示だけをcommit・pushの許可と扱わない。対象の規則に従って各操作の明示指示を受ける。
4. 保存状態を確認する。
   - GitHub管理中：必要なpushが成功し、対象branchのGitHub上のHEADと基準commitが一致し、送る側の作業ツリーがcleanである。
   - ローカルGitのみ：必要なcommitが存在し、送る側の作業ツリーがcleanで、受け取る側がそのcommitを取得できる。
   - Gitなし：必要なファイルが保存済みで、受け取る側に同じ一式を渡せる。会話内だけに残る作業情報がない。
5. 該当する保存条件を確認できてから、最終版の引き継ぎ文を渡す。満たせない場合は、最終版として渡さず、未完了の内容と理由を報告する。変更がない場合、新しいcommitは不要である。

## 4. 確認状態

- `VERIFIED`：記載したEvidenceで、記載者が実際に確認した。
- `UNVERIFIED`：情報はあるが、必要な確認ができていない。
- `ASSUMPTION`：作業上の仮定として明示した。
- `N/A`：その案件・保存方式には該当しない。

送る側の`VERIFIED`は、受け取る側の確認結果を意味しない。受け取る側は正本を取得し、照合結果を改めて報告する。

## 6. 利用上の原則

コピー用テンプレートの全項目を毎回長文で埋める必要はない。必要な情報は一箇所に記載し、別の欄で要約し直して値を増やさない。

受け取る側は引き継ぎ文を作業の入口として使い、取得した正本と照合する。保存方式に応じた確認ができない場合は、その範囲を`UNVERIFIED`と報告し、対象案件の規則に従って作業可否を判断する。

GitHub管理中またはローカルGitのみの案件を読取専用で受け取る場合は、Repository、branch、取得したcommit SHAを確認し、SHAが確認できない場合は未確認と報告する。Gitなしの案件では、保存済みファイルの所在・一覧・保存時点を確認し、Git固有の値は`N/A`とする。読取専用ではローカルWorkspace、ローカルHEAD、worktreeの確認を必須とせず、ローカルGit状態が未確認であることだけを理由に停止しない。Repositoryにローカル変更を加える前には、対象Repositoryの作業規則に定められた同期ゲートを実施する。Gitなしの案件では対象ファイルの保存規則を確認する。
