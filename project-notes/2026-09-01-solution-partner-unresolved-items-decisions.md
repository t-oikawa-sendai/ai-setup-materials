## 2. 背景と基本方針

対象利用者は職業訓練校等のIT初学者である。

要件定義・設計を厳密にしすぎると、初学者が判断できない未決事項によって次工程へ進めなくなる。一方、AIが未指定事項を一般論や推測で補完すると、Userが決めた仕様とAIが作った仕様が混在し、初学者が混乱する。

このため、基本方針を次のとおり確定する。

- AIは未決事項を勝手に補完・確定しない。
- 未決事項が残ること自体は許容する。
- ただし、次工程開始前に決定が必要な事項と、実装段階まで持ち越せる事項を区別する。
- 初学者を不必要に止めない一方、実装成立に必要な判断を未決のまま通過させない。
- 判断はUserが行い、Solution Partnerは必要なときに判断を支援する。

## 3. 未決事項の分類

Solution Partnerが未決事項を次の2区分へ分類する。

1. `次工程開始前に決定必須`
2. `実装段階まで持ち越し可能`

分類はAIが影響度に基づいて行う。

### 3.1 最小判定基準

- 未決のままだと実装開始そのものができない、または主要な設計が変わり得る事項
  - `次工程開始前に決定必須`
- 実装開始には支障がなく、その処理を実装する時点までに決めればよい事項
  - `実装段階まで持ち越し可能`

分類に必要な情報が不足し、Solution Partnerがどちらへ分類すべきか判断できない場合は、安全側へ機械的に寄せない。分類に必要な情報だけをUserへ確認し、その回答後に分類する。

## 4. 次工程開始前に決定必須の扱い

`次工程開始前に決定必須` が1件以上存在する場合、次工程へ進まない。

Solution Partnerは次を行う。

1. 対象の未決事項を自動表示する。
2. なぜ今決める必要があるのかを、初学者にも分かる言葉で丁寧に説明する。
3. 「表示しますか」という確認は挟まず、そのままASKMEを開始する。
4. 全件が解消されるまで次工程へ進まない。

停止理由の説明は、単なる「未決だから」ではなく、その未決事項が次工程・主要設計・実装成立へどう影響するため今必要なのかを理解できる内容とする。

## 5. 実装段階まで持ち越し可能な未決事項の扱い

`次工程開始前に決定必須` が0件で、`実装段階まで持ち越し可能` が存在する場合は、Userが未決事項を今確認・決定するか選べる。

### 5.1 チャット上の表示確認

Solution Partnerは未決事項があることと件数を明示し、詳細をチャット上で表示するかUserへ確認する。

Userが詳細表示を希望しない場合も、次を表示する。

- 次工程開始前に決定必須：0件
- 実装段階まで持ち越し可能：N件
- 実装段階でN件の未決事項を決定する必要があること

この「表示しますか」は、ASKME開始前にチャット上で詳細を見るかどうかだけを意味する。
最終設計文書の `補足A：未決事項一覧` から未決事項を省略する意味ではない。

### 5.2 詳細表示後の選択

持ち越し可能な未決事項を表示した場合、Userは次から選択できる。

- 全て決定する
- 一部を決定する
- 今は決定しない

全て決定する場合は全対象についてASKMEを行う。
一部を決定する場合は選択された項目だけASKMEを行い、残りは未決事項として保持する。
今は決定しない場合は、そのまま持ち越す。

## 6. 再検討ルート

一度 `実装段階まで持ち越し可能` として保留した未決事項も、Userが希望すれば何度でも設計段階で再検討できる。

Userが「やはり今決めたい」「設計段階で検討したい」等を示した場合は、`補足A：未決事項一覧` を再参照し、対象項目についてASKMEへ戻る。

決定後は次を行う。

1. 決定内容を設計書本文の該当箇所へ反映する。
2. `補足A：未決事項一覧` から決定済み項目を削除する。
3. 未決事項件数を再計算する。

`補足A` は履歴表ではなく、現在残っている未決事項だけを保持する。

## 7. 補足A：未決事項一覧

設計文書の完成時または次工程への引渡し時には、文書末尾に固定名称 `補足A：未決事項一覧` を設ける。

設計途中のすべての回答へ毎回付ける必要はない。Userが途中で要求した場合は表示できる。

### 7.1 件数表示

未決事項が0件でも省略しない。

常に次の3件数を固定形式で表示する。

```text
未決事項 合計：N件
- 次工程開始前に決定必須：N件
- 実装段階まで持ち越し可能：N件
```

0件の場合も次のように明示する。

```text
未決事項 合計：0件
- 次工程開始前に決定必須：0件
- 実装段階まで持ち越し可能：0件
```

0件を明示することで、記載漏れではなく未決事項が存在しないことをUserおよび次工程が確認できるようにする。

### 7.2 一覧の必須項目

未決事項一覧の各項目は次の最小構成とする。

| ID | 未決事項 | 区分 | 理由 |
|---|---|---|---|

`理由` には、なぜ次工程開始前に決定が必要なのか、またはなぜ実装段階まで持ち越せるのかを、初学者にも分かる表現で記載する。

決定済み項目は一覧へ履歴として残さず、設計本文へ反映して一覧から削除する。

## 8. ASKMEの判断支援

ASKMEでは、最初から大量の説明や判断材料を提示しない。

基本フローは次とする。

1. まず質問を簡潔に提示する。
2. Userが判断できる場合はそのまま決定する。
3. Userが `検討`、`意味不明`、`決められない`、`違いを説明して` 等を示した場合に、必要な判断材料を追加する。
4. 判断材料を確認した後、同じ未決事項についてUserが決定する。

判断材料として必要に応じて示す内容は次を含み得る。

- 何を決める質問なのか
- なぜ決める必要があるのか
- 選択肢の違い
- 設計・実装への影響
- 必要な場合のみSolution Partnerの推奨案と理由

判断材料を提示しても、AIがUserの代わりに仕様を確定しない。

この動作をASKMEの共通ルールとして扱う。

## 9. Code Generatorとの共通認識

`補足A：未決事項一覧` は、Solution PartnerとCode Generatorの間で未決事項を引き継ぐインターフェースとして使用する方針を確定する。

Code Generator側には将来、少なくとも次の認識を持たせる。

- `補足A：未決事項一覧` がある場合は必ず確認する。
- 未決事項を独自判断・一般論・推測で補完しない。
- `次工程開始前に決定必須` が残る設計書は実装対象として進めない。
- `実装段階まで持ち越し可能` は、該当処理の実装時点まで未決として保持する。

ただし、Code Generator Personaの実変更はSolution Partner側の反映確定後の別工程とし、本記録では変更しない。

## 10. ASKMEの不要確認禁止

不必要なASKMEは禁止する。

次はASKMEへ回さない。

- 既に確定済みの事項
- 既存ルールから一意に導ける事項
- AI側で確認・判断可能な事項
- 同じ内容の重複確認

本当にUser判断が必要な未決事項だけASKMEする。
