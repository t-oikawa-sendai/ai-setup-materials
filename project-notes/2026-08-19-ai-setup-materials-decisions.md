## 1. プロジェクトの目的

GitHubリポジトリ `ai-setup-materials` を、生徒へ配布可能なAI活用教材として完成させる。

生徒が生成AIを学習・開発・調査に活用できる環境を提供する。

Gemini内の4Gem運用を基本ルートとしつつ、ChatGPT・Gemini・Cursor・Claudeなど、**AIサービス自体を役割ごとに分けた運用環境にも対応する。**

---

## 2. 教材の最優先方針

本教材は、**開発作業の効率化・合理化そのものを目的とするものではない。**

生徒自身が**オーケストレーター**となり、

- 調査
- 設計
- 実装
- レビュー

を担当するAIを使い分ける。

各AIの出力を生徒自身が確認し、次の工程へ受け渡し、必要に応じて前工程へ戻って修正・再検証する。

この一連の流れを**擬似的なループエンジニアリング**として体験することで、

- AIへの適切な指示
- AIとの役割分担
- AI出力の確認
- 検証
- 修正
- 工程間の受け渡し

を体験的に学ぶことを第一義とする。

### 基本イメージ

```text
生徒 = オーケストレーター

Research AI
    ↓
Design AI
    ↓
Implement AI
    ↓
Review AI
    ↓
問題あり
    ├─ 実装へ戻す
    ├─ 設計へ戻す
    └─ 必要なら調査へ戻す
```

AIに開発全体を自動的に任せるのではなく、生徒自身がループを管理・判断することを重視する。

## 3. 第一次KGI

生徒が生成AIを学習・開発・調査に活用できる教材を完成させる。

### 標準ルート

Gemini内で4つのGemを作成して利用する。

役割：

1. 設計者
2. 実装者
3. レビュアー兼セキュリティチェッカー
4. 情報リサーチャー

各Gemについて以下を完成させる。

- 正式名称
- 説明
- Persona
- 使い分け
- 工程間の受け渡し方法

### 発展ルート

AIサービス自体を役割ごとに分けて運用できる構成も提供する。

例：

```text
Gemini  → 調査
ChatGPT → 設計
Cursor  → 実装・テスト
Claude  → 独立レビュー
```

生徒がGeminiだけに限定されず、自身の判断で複数AIによる責務分離へ発展できる構成とする。

## 5. リポジトリ構成の方向性

現時点の構成骨格は以下とする。

```text
ai-setup-materials/
├─ README.md
│
├─ setup/
│  └─ GEMINI_SETUP.md
│
├─ personas/
│  ├─ education/
│  │  ├─ README.md
│  │  ├─ GEM_DESIGNER.md
│  │  ├─ GEM_IMPLEMENTER.md
│  │  ├─ GEM_REVIEWER.md
│  │  └─ GEM_RESEARCHER.md
│  │
│  └─ reference/
│     ├─ CHATGPT_PERSONA.md
│     ├─ CLAUDE_PERSONA.md
│     ├─ CURSOR_PERSONA.md
│     └─ GEMINI_PERSONA.md
│
├─ prototype/
│  └─ gemini-live-interviewer/
│
└─ project-notes/
```

### `personas/education/`

Gemini内で4Gemを運用するための教育用Personaを配置する。

`GEM_` プレフィックスを使用する。

### `personas/reference/`

ChatGPT・Gemini・Cursor・Claude等、AIサービス自体を分けて運用する場合の参考Personaを配置する。

### `prototype/`

第二次KGIなど、正式教材化前のPoC・実機検証対象を配置する。

### `project-notes/`

打ち合わせ、途中整理、引き継ぎ等、正式成果物ではない作業メモを配置する。

## 7. 生徒の環境設定に関する教育方針

生徒ごとの環境設定テンプレートは用意しない。

あえて講師環境の値を設定した状態で配布する。

狙いは以下の体験をさせることにある。

```text
講師環境値のまま実行
        ↓
生徒環境ではエラー
        ↓
原因を調査
        ↓
環境依存値を発見
        ↓
自分の環境に合わせて修正
        ↓
正常動作
```

これにより、

**環境依存値は正確に設定しなければ正常に動作しない**

ことを実体験させる。

ただし、

- APIキー
- パスワード
- トークン
- その他秘密情報

の実値は教材へ含めない。

## 9. ChatGPTのGitHub WRITE権限

基本原則として、ChatGPTは正式成果物を直接変更しない。

ただし、正式成果物ではない作業メモについては例外とする。

### ChatGPTが直接WRITE可能

```text
project-notes/
```

対象：

- 打ち合わせメモ
- 作業途中の論点整理
- 未決事項
- TODO
- 引き継ぎメモ
- 決定前の候補整理

### ChatGPTが直接WRITEしない

- `README.md`
- `setup/`
- `personas/`
- `prototype/`
- 仕様書
- その他正式成果物

正式成果物は、

```text
ChatGPT
設計・指示
    ↓
Cursor
作成・変更・検証・Git反映
    ↓
ChatGPT
GitHub上の実物確認
```

の責務分担を維持する。

### 原則

**技術的に操作可能であることと、責務上操作してよいことを分離する。**

## 10. ChatGPTメモリの扱い

ChatGPT内部のメモリをプロジェクトの正本として扱わない。

理由：

- 情報が欠落する可能性がある
- 誤認する可能性がある
- AI自身の記憶をAI自身だけで検証する構造になる

そのため、重要な設計判断ではGitHub上の実物を確認する。

```text
GitHub上の実物
        ↓
ChatGPTがREAD
        ↓
現状確認
        ↓
設計・判断
```

正式成果物のWRITEはCursorの責務を維持する。

## 参考情報：IBMによるLoop Engineering

IBMはLoop Engineeringを、ユーザーが定めた目標へ向けて、AIエージェントを反復的に導くエージェント型ワークフローを設計する考え方として説明している。

基本的なループは、

1. Goal（目標）
2. Action（実行）
3. Observation（観察）
4. Adjustment（調整）

という流れで構成される。

本来のLoop Engineeringでは、AIエージェントが最小限の人間介入でこのループを反復する方向が重視される。

本教材では、そのループを完全に自動化するのではなく、**生徒自身がオーケストレーターとなって意図的にループを管理・実行する。**

この違いから、本教材ではこれを**「擬似的なループエンジニアリング」**として位置付ける。
