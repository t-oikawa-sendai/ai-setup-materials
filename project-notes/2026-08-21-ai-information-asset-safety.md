# AI情報資産保全・復旧方針

- 作成日：2026-08-21
- Status：CONFIRMED

## 1. 背景

AIによる決定事項の統合・更新で、過去の確定事項と後続の変更決定を正しく扱えず、旧情報を現行情報として復活させる問題が発生した。

具体例として、Education用4Gemでは `Implementer` から `Code Generator` へ変更された後続決定があるにもかかわらず、AIが古い `Implementer` を現行4Gemとして統合記録へ再混入させた。

この結果、ここまで積み重ねてきた重要な情報資産の信頼性が毀損した。

原因分析だけでは毀損した情報資産は復旧しない。時間と手間がかかっても、一次資料・既存記録・現物を基準に再構築する。

## 2. AI能力に関する安全前提

このRepositoryでは、AIの能力を過信しない。

AIは次の問題を起こし得るものとして扱う。

- 過去の決定を完全には保持できない
- 新旧決定の上書き関係を取り違える
- 旧情報を現行情報として復活させる
- 複数文書の統合時に確定事項を欠落させる
- ファイルが存在することと、現在採用されていることを混同する
- 推論・補完を確定事項へ混入させる
- 自分が整理できていると誤認する

したがって、重要情報資産の保全をAIの記憶・会話履歴・自己認識だけに依存しない。

## 3. 安全原則

1. AIは「自分の認識が正しい」と前提にしない。
2. 重要な決定を扱う前に、Repository内の正本・決定記録・現物を確認する。
3. 名称変更、役割変更、採用・廃止、置換がある場合は、単純な情報追加ではなく時系列と上書き関係を確認する。
4. `CURRENT / SUPERSEDED / UNRESOLVED` を分離する。
5. 既存ファイルの存在だけを根拠に「現行採用」と判断しない。
6. 統合前に競合・矛盾・旧決定復活の有無を確認する。
7. 解釈が一意でない場合だけユーザーへ確認し、AI側で確認可能な事項を個別質問へ転嫁しない。
8. 「統合済み」「確定」「正本」と宣言する前に、最新性・上書き関係・欠落の検証を行う。
9. 重要な決定はこまめにGitHubへ記録し、後から大量の会話履歴を一括再構成する必要を減らす。
10. 誤った統合が発覚した場合、原因説明だけで復旧扱いにしない。信頼できる資料から再構築し、検証完了後に正本を復旧する。

## 4. 現在の復旧対象

`project-notes/2026-08-21-education-4gem-design-decisions.md` は、Education用4Gemの `Implementer` / `Code Generator` の新旧関係を誤って統合していることが確認された。

そのため、再構築完了までこの文書を現行設計の正本として扱わない。

確定している最新名称：

```text
Researcher
Solution Partner
Code Generator
Reviewer
```

`Code Generator` と、Cursor等で実装を担当する `Implementer` は別概念として扱う。

ただし、旧 `Implementer` の責務を機械的にすべて `Code Generator` へ置換してはならない。役割変更後の責務・戻し先・文書連携は、既存資料を再確認して再構築する。

## 5. 復旧方法

1. GitHub上の関連決定記録を時系列で収集する。
2. Education Personaの現物を確認する。
3. README・CURRENT・関連文書を照合する。
4. 各事項を `CURRENT / SUPERSEDED / UNRESOLVED` に分類する。
5. 資料だけで一意に決まらない事項のみユーザーへまとめて確認する。
6. 確認済み事項から順にGitHubへこまめに記録する。
7. 再構築が完了するまで、誤った統合記録を正本扱いしない。

## 6. 復旧完了条件

- Education用4Gemの最新名称・責務・境界が一意に整理されている
- 旧決定と現行決定が明確に区別されている
- `CURRENT.md` と決定記録が一致している
- README・Persona・管理文書に旧情報の誤混入がないことを確認している
- 不明点が推論で埋められていない
- ユーザーが必要な未決事項を確認できる状態になっている
